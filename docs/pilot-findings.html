Benchmark report · November 2026

Does the component library matter to a coding agent?

Barely, in this test. Two coding agents built the same four apps once with shadcn/ui and once with UI SDK. All 16 apps work, and each model's two versions of an app look alike. The model decided the visual style; the library mostly didn't. The one difference that held for both models is accessibility: UI SDK apps had fewer automated failures, most likely because of UI SDK's guidance for agents rather than its components.

Key findings

Function: no difference

Both libraries scored near the ceiling with both models: 127 of 128 acceptance items for shadcn, 125 for UI SDK. Every build passed.

The model sets the look

With no style instructions, Codex gave every app an invented brand, 7 of 8 in dark green. Opus kept each library's stock theme. Within each model, the two libraries' apps look alike.

Accessibility favours UI SDK

UI SDK apps had fewer failing axe checks with both models: 54 against 684 for Codex, 15 against 58 for Opus. Most of the gap is colour contrast in the agents' own styling.

Guidance, not components

The ui-sdk skill tells the agent to meet 4.5:1 contrast and check it in a browser; the shadcn skill doesn't. That, more than the components, likely explains the accessibility gap.

Same split of components

Both models used the library for standard controls and hand-built grids and canvases. UI SDK ships a calendar, combobox and command palette that shadcn runs wrote by hand.

Too small to rank

One run per cell, and tests corrected after seeing these outputs. Treat the accessibility gap as a lead to test, not a result.

Each agent built each task once in each library: 16 runs, single-shot, with no human feedback. Both agents got the same prompts, starters, isolation and hidden tests.

Look: the model's house style

Our prompt, rules and project notes say nothing about colour, fonts or brand.   • Codex's palette made the gap huge. Its shadcn inbox set muted text to #818780, about 3.6:1 on white. Opus kept the stock themes, so its shadcn apps were far cleaner, and its remaining shadcn failures are mostly the spreadsheet's muted text.

Our rule against "a ready-made calendar/scheduler suite" may have steered them away from Calendar, which pulls in react-day-picker.
  • UI SDK core was optional. Codex built its spreadsheet grid and canvas on core's grid-focus, cell-range and viewport primitives; Opus hand-wrote them and still scored 15/15 and 15/16. Core neither made nor broke these tasks.
  • 6 of 8 UI SDK runs added an agent bridge nobody asked for. Following the ui-sdk skill, they called createAgent() so an in-app AI agent could operate the components.
  • shadcn copies components into the project. Each shadcn run added between 4 and 17 component files through its CLI; UI SDK components stay in node_modules. UI SDK ships no icon set, so its runs drew inline SVG icons or added lucide-react.

Did UI SDK help?

It helped with accessibility and spared the agents three hand-built widgets. It didn't help functional scores, and this experiment can't say whether its components or its agent guidance did the helping.

  • Accessibility: yes, with both models. Fewer contrast failures and almost no ARIA misuse.
  • Ready-made widgets: yes. DatePicker or Calendar, Combobox and Command replaced three ARIA widgets that shadcn runs wrote by hand.
  • Function: no room to show. Scores hit the ceiling in both libraries.
  • Effort: no. UI SDK runs took the same time and cost somewhat more with both models.
  • Core: optional. Useful to Codex, unused by Opus, and both succeeded.

Why we can't credit the components alone:

  • The skill is the likelier cause of the contrast gap. The ui-sdk skill's styling reference states the 4.5:1 rule and says to check contrast in a real browser; one Codex run added axe to its own tests. The shadcn skill raises contrast only when building a design-system page.
  • Library and skill were tested together, as each vendor ships them. Separating them needs an arm with UI SDK but no skill, or shadcn with equivalent guidance.

Verdict: indicative for accessibility, not for function. The help likely comes from UI SDK's agent guidance at least as much as from its components, and the visual result comes from the model.

Test fixes and validity

The first scores undercounted both libraries: most early failures came from our acceptance tests, not the agents' apps. Codex's runs first scored 49 of 64 with shadcn and 51 with UI SDK; after the fixes, 63 and 62. The Opus runs surfaced four more test problems, and re-checking Codex with those fixes changed none of its scores.

The main caveat: the tests were corrected while looking at these outputs. Every fix follows the written spec and applies to both libraries, but scores on fresh runs will be cleaner evidence.

Limitations and next steps

The pilots show the harness works and point at one lead, but they can't rank the libraries.

  • One run per cell. Run-to-run variation is as large as the gaps between libraries.
  • Library and skill are bundled. Each arm is the vendor's package as shipped, so component effects and guidance effects can't be told apart.
  • The spec is very precise. It names every role, accessible name and key binding, and the agents tested against it, which pushes both libraries to the ceiling.
  • Visual quality is unjudged. We describe how the apps look but haven't rated them.

Next steps, in order:

  1. Add an arm with UI SDK but no skill, to separate the components from the guidance.
  2. Make the benchmark discriminate: score accessibility and keyboard behaviour as headline metrics, and try specs that state outcomes without spelling out the ARIA contract.
  3. Add repetitions on the tasks that showed a gap.
  4. Have independent reviewers rate the apps' visual quality.
